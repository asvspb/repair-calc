## 2. Архитектурная модель (текущая)

Состояние приложения после миграции управляется **zustand** с разбиением на слайсы:

```
src/store/
├── useProjectStore.ts      # композиция слайсов (create + combine)
├── createProjectSlice.ts   # проекты + persistence + sync-поля
├── createObjectSlice.ts    # объекты недвижимости
├── createRoomSlice.ts      # комнаты
├── createSyncSlice.ts      # слушатели синхронизации
└── types.ts                # ProjectSlice/RoomSlice/ObjectSlice/SyncSlice → StoreState
```

**Оценка:** разбиение на слайсы — шаг в правильном направлении (устранён
god-context `ProjectContext.tsx` на ~982 строки). Однако `ProjectSlice` всё ещё
накапливает инфраструктурные обязанности — см. раздел 4.A.

### Слоистость

```
api/        →  внешний слой (HTTP, storage providers, prices)
contexts/   →  Auth + WorkTemplate (UI-scoped)
hooks/      →  domain-driven hooks (useGeometryState, useMaterialCalculation, ui/*)
store/      →  глобальное состояние (slices)
utils/      →  чистые функции (geometry, costs, factories, idMapper...)
components/ →  UI (auth, geometry, layout, objects, projects, rooms, works, summary, ui)
```

Проверка: `utils/` и `api/` **не** импортируют из `components/` — слойность
соблюдена (без reverse-зависимостей).

## 4. Скрытые архитектурные дефекты (Blast Radius)

### A. `ProjectSlice` нарушает Single Responsibility

**Локация:** `src/store/types.ts:4-28`, `src/store/createProjectSlice.ts` (609 строк).

Слайс содержит поля инфраструктурных ответственностей:

- **auth:** `isAuthenticated`, `setIsAuthenticated`
- **sync:** `isSyncing`, `lastSavedToServer`, `lastTotalsSave`, `totalsSaveError`, `roomSyncError`, `scheduleTotalsSave`
- **persistence:** `lastSaved`, `saveError`

При этом существует `createSyncSlice.ts`, чьи обязанности пересекаются с полями
проектного слайса → риск гонок между `scheduleSave` / `scheduleTotalsSave` /
`initSyncListeners`.

**Blast radius:** средний (4 файла слайсов + `App.tsx` + синх-провайдеры).
**Рекомендация:** вынести `auth`/`sync`-состояние в отдельные слайсы; оставить
`ProjectSlice` только доменными полями и CRUD.

### B. Бизнес-логика и ID-генерация в компоненте

**Локация:** `src/App.tsx:103-123` (`handleCopyProject`).

- Глубокий клон через `JSON.parse(JSON.stringify(sourceProject))` прямо в
  обработчике JSX.
- Генерация ID дублирована: `local-${Date.now()}`, `obj-${...}`,
  `room-${Date.now()}-${Math.random()...}` — нарушение DRY.
- `Date.now()` без монотонности → потенциальные коллизии при быстром вызове
  (race state).

**Рекомендация:** вынести клон + ID-генерацию в `utils/factories.ts`
(`cloneProject(project): ProjectData`), использовать монотонный счётчик / `crypto.randomUUID()`.

### C. Test-seam в production-пути

**Локация:** `src/App.tsx:239` — `localStorage.getItem('e2e-test-mode')`.

Тестовая логика утекла в боевой код. Обход auth-проверки по флагу в localStorage
— точка компрометации.

**Рекомендация:** заменить на `import.meta.env.DEV` или инжектируемый флаг
через dependency injection.

### D. Native UI в компоненте (запрет стандартом)

**Локация:** `src/App.tsx:163` — `window.confirm('Удалить объект?...')`.

В проекте уже есть `src/components/ui/ConfirmDialog.tsx`, но он **не
используется** в этом месте. → Заменить на существующий компонент.
