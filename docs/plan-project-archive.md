# Plan: Архив проектов — разделение UI-удаления и удаления из БД

- **Дата:** 2026-08-12 (ревизия 2 от 2026-08-25 — правки по cross-model ревью)
- **Автор/агент:** Архитектор-контролёр (ZCode)
- **Статус:** approved (владелец, 2026-08-25: ревизия 2 проверена grep'ом, все 6 правок ревью на месте; блокер закрыт дизайном)
- **Связанные задачи:** обсуждение с владельцем 2026-08-12; cross-model ревью 2026-08-25 (1 блокер в T1 устранён, guard'ы T2/T3 усилены)

## 1. Постановка задачи (WHAT и WHY)

**Что делаем** (1–3 предложения, без технических деталей):
Разделяем «удалить проект из списка» и «удалить проект из базы». Обычное удаление в UI прячет проект в архив (данные сохраняются полностью); настоящее удаление из БД — отдельное осознанное действие «Удалить навсегда» только через меню «Настройки → Архив».

**Зачем** (какую проблему решаем / какую ценность несём):
Экспериментальные/черновые проекты можно freely удалять из рабочей списка, не боясь потерять данные — архив хранит всё до явного решения. Необратимое удаление защищено двумя шагами (архивация → подтверждение с вводом имени), случайное уничтожение данных исключено.

## 3. Технический подход (HOW)

**Выбранное решение:** трёхуровневая модель поверх существующего soft-delete.

Ключевой факт (проверен по коду): `ProjectRepository.delete` **уже soft-delete** — ставит `deleted_at` на проекте/объектах/комнатах (`project.repo.ts:127`), строки не покидают БД, purge-воркера нет, все чтения фильтруют `deleted_at IS NULL`. Фундамент уже готов; добавляем недостающее — доступ, восстановление и hard-delete.

| Уровень                | Действие                  | Реализация                                                                                  |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------------------------- |
| 1. «Удалить» в UI      | архивация                 | как сейчас (`DELETE /api/projects/:id` → soft-delete); меняется только семантика/UX-подпись |
| 2. «Настройки → Архив» | просмотр + восстановление | `GET /api/projects/archived`, `PATCH /api/projects/:id/restore`                             |
| 3. «Удалить навсегда»  | единственный real-DELETE  | `DELETE /api/projects/:id/permanent` → транзакция + FK CASCADE                              |

**Ключевые решения:**

- **Reuse `deleted_at` вместо новой колонки** — ноль миграций. Архивная пометка = существующий механизм.
- **Атомарная архивация с единым JS-штампом** (блокер из ревью): текущий `delete()` — три раздельных `execute()` в autocommit, `CURRENT_TIMESTAMP` в них НЕ гарантированно совпадает. T1 рефакторит `delete()`: `const archivedAt = new Date()` один раз в JS → передаётся параметром во все три UPDATE; плюс обёртка в `transaction()` (атомарность: либо весь архив, либо ничего). Унифицируется с существующим прецедентом `object.repo.ts:132` (`deleted_at: new Date()`).
- **Restore по совпадению штампа**: возвращаются только дети, архивированные вместе с проектом (`deleted_at = штампу проекта`). Объект, удалённый из UI _до_ архивации проекта (штамп старше), воскрешать нельзя — и не будет. Корректность гарантируется единым JS-штампом (см. выше) + **blocking-тестом на идентичность штампов**.
- **Guard'ы симметричны**: `hardDelete` отказывает для активного проекта (`deleted_at IS NULL` → 409 «сначала архивируй»); `restore` симметрично отказывает для активного проекта (→ 400 «нечего восстанавливать»).
- **Контракт ответа `restore`**: полный проект с объектами и комнатами (как `findByIdWithObjects`) — клиент вставляет его в стор без повторного pull.
- **`hardDelete`: счётчики до DELETE** — `COUNT(objects/rooms)` в той же транзакции, что DELETE и запись в `audit_log` (каскад уничтожит строки — считать после невозможно).
- **Guard hard-delete**: real-DELETE отказывает, если проект активен (`deleted_at IS NULL`) — сначала архивация, потом удаление навсегда. Двойное осознанное действие.
- **`sync/pull` не меняется** — он уже исключает `deleted_at IS NOT NULL`; воскрешения нет.
- **UX-защита**: «Удалить навсегда» требует ConfirmDialog **с вводом имени проекта**.

**Альтернативы:** колонка `is_archived` (отклонено: дублирует `deleted_at`, требует миграцию, две «правды» о скрытости); клиентский список скрытых ID в localStorage (отклонено: ломается на втором устройстве и при чистке хранилища).

## 4. План реализации (задачи)

- [ ] **T1 (server/repo):** (a) **рефактор `delete()` в атомарную архивацию**: `transaction()` + единый `const archivedAt = new Date()` во все три UPDATE (блокер ревью); (b) `findArchivedByUserId(userId)`, `findArchivedByIdAndUserId(id, userId)`; (c) `restore(id, userId)` — guard «проект архивен», дети по штампу проекта, транзакция; (d) `hardDelete(id, userId)` — guard «только архивный», `COUNT(objects/rooms)` **до** DELETE в той же транзакции, `DELETE FROM projects` → CASCADE, вставка в `audit_log` там же, вернуть `{objects, rooms}`. Тесты: **blocking-тест идентичности штампов** (проект/объекты/комнаты получают один `deleted_at`), restore-семантика (объект, удалённый до архивации, не возвращается), guard'ы, каскад+счётчики.
- [ ] **T2 (server/routes+schemas):** `GET /projects/archived` (AuthRequest, без IS NULL), `PATCH /projects/:id/restore` — **guard: активный проект → 400 «нечего восстанавливать»**; ответ = полный проект с объектами/комнатами; `DELETE /projects/:id/permanent` — guard активного → 409; Zod idParam, winston-лог со счётчиками. Интеграционные тесты через агрегирующий роутер (по образцу `routeMounting.test.ts`), включая guard-кейсы.
- [ ] **T3 (client/api+store):** `src/api/projects.ts` — `getArchivedProjects/restoreProject/permanentDeleteProject`; `createProjectSlice.deleteProject` — комментарий/семантика «архивация» (механика не меняется); **hard-delete: удалить проект из `state.projects` (если вдруг там) + вычистить idMapper-маппинги проекта и ВСЕХ его объектов/комнат** — иначе исходящий sync попытается запушить изменения несуществующего на сервере проекта.
- [ ] **T4 (client/UI):** секция «Архив» в ProjectSettings (или `ArchivePanel.tsx`): список (имя, дата архивации, счётчики объектов/комнат), кнопки «Восстановить» / «Удалить навсегда» (ConfirmDialog + ввод имени для последнего). Гостевой режим — секция скрыта.
- [ ] **T5 (docs):** `INDEX.md` (новые эндпоинты в API-таблице), `developer_log.md` append, этот план → статус done.

Порядок: T1 → T2 → T3 → T4 → T5 (последовательно; T3 частично параллелен T2).

## 5. Тестирование

**Как проверяем, что фича работает:**

- Unit/integration (server): **идентичность штампов при архивации (blocking)**; архивация → не виден в `findAllByUserIdWithObjects`, виден в `findArchivedByUserId`; restore возвращает проект с детьми по штампу (объект, удалённый раньше, не возвращается); **restore активного → 400; hard-delete активного → 409**; hard-delete архивного → каскад, счётчики (посчитаны до DELETE); чужой проект → 404.
- Ручной сценарий владельца (дословно): удалить P1 из UI → создать P2 → изменить → удалить → загрузить P3 → изменить → удалить. В архиве лежат P1, P2, P3; в списке UI — пусто. «Восстановить» P3 → он в списке со всеми изменениями. «Удалить навсегда» P1 (с вводом имени) → в БД (`psql count`) P1 отсутствует, P2/P3 остаются.
- Sync: вход на втором устройстве/refresh — архив не воскрешается в списке.

**Acceptance criteria** (критерии готовности):

- [ ] UI-«удалить» никогда не удаляет строки из БД (только `deleted_at`)
- [ ] Архив доступен из настроек: список, восстановление, удаление навсегда
- [ ] Hard-delete возможен только для архивного проекта и только из настроек
- [ ] Restore не воскрешает объекты, удалённые до архивации проекта
- [ ] `sync/pull` не отдаёт архивные проекты
- [ ] Гость: архив скрыт, локальное поведение не изменилось
- [ ] `npm test` / `npm run lint` / `npm run lint:deps` зелёные; CI green

## 6. Риски и альтернативы

| Риск                                                       | Вероятность        | Смягчение                                                                                                                                        |
| ---------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Restore по штампу хрупок (штампы расходятся при архивации) | устранено дизайном | T1 (blocking): единый JS-штамп `new Date()` + `transaction()` вокруг трёх UPDATE; blocking-тест идентичности штампов — без него merge невозможен |
| «Воскрешение» через старый клиент/кэш                      | низкая             | pull уже фильтрует; убрать проект из локального стора при архивации (уже делается в deleteProject)                                               |
| Случайный hard-delete                                      | низкая             | guard «только архивный» + ввод имени + отдельный эндпоинт                                                                                        |
| Потеря данных при hard-delete (cascade шире ожидаемого)    | низкая             | счётчики в ответе API (видно, что удалилось) + audit_log                                                                                         |
| Рост БД от вечного архива                                  | принято            | осознанное решение владельца; purge не заводим; опция retention — вне scope                                                                      |

**Альтернативы, рассмотренные и отклонённые:** см. §3 (is_archived, клиентский hide-list).
